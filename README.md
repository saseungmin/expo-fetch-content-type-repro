# Expo Fetch Content-Type reproduction

A standalone Expo app comparing named `expo/fetch` with React Native's global
Fetch against a local Node HTTP echo server. No S3, credentials, image picker,
company application code, or external echo service is used.

Repository: https://github.com/saseungmin/expo-fetch-content-type-repro

Upstream issue: https://github.com/expo/expo/issues/51449

```sh
git clone https://github.com/saseungmin/expo-fetch-content-type-repro.git
cd expo-fetch-content-type-repro
```

## Run on an iOS simulator

```sh
npm ci
npm run server
```

In another terminal:

```sh
npm run ios
```

Allow the simulator to open the project in Expo Go. Tests run automatically;
the **Run again** button repeats them. This project uses port 8787 for the echo
server and 8091 for Metro. The Node IPv4-first flag avoids a local IPv6-only
Metro binding while the simulator project URL points to 127.0.0.1.

`artifacts/wire-results.json` is generated by your running server and accumulates
the current server session's observations. The version-specific JSON files are
saved evidence from the four verified platform/version runs, not files automatically generated by
every new run.

`.env` sets `EXPO_PUBLIC_USE_RN_FETCH=1` deliberately: global Fetch is the RN
control, while the named import from `expo/fetch` remains Expo's implementation.
The app and server metadata confirm that `globalThis.fetch !== expoFetch`.

## Run on an Android emulator

Start an Android API 36 emulator with enough free space for Expo Go. Then run:

```sh
npm ci
npm run server
```

In another terminal, connect the echo-server port and start Expo:

```sh
adb reverse tcp:8787 tcp:8787
npm run android
```

Expo CLI connects Metro through adb reverse. If several devices are connected,
use `adb -s <serial> reverse tcp:8787 tcp:8787` for the selected emulator.
No LAN IP or external HTTP service is needed. Tests run automatically.

## Cases

Each request sends the same 12 ASCII bytes (`test payload`) using `PUT` and
an explicitly supplied Content-Type in a `Headers` object.

| Body | Explicit header | Expo receives | RN receives |
| --- | --- | --- | --- |
| Blob type `text/plain` | `application/octet-stream` | `text/plain` | `application/octet-stream` |
| Blob type empty | `image/jpeg` | empty string | `image/jpeg` |
| Blob type `text/plain` | `text/plain` | `text/plain` | `text/plain` |
| ArrayBuffer | `image/jpeg` | `image/jpeg` | `image/jpeg` |
| Response.blob(), source response has no Content-Type | `image/jpeg` | empty string | `image/jpeg` |

The server captures the received headers, request body, and implementation
label in `artifacts/wire-results.json`. The last case reads from a controlled
HTTP response without Content-Type; it is not a file:// or image-picker test.

## Verified environment

- Expo JS package: **57.0.24 and 57.0.28**, tested in separate fresh Metro bundles.
- Final project dependency: Expo **57.0.28**, React **19.2.3**, RN **0.86.3**.
- Expo Go native app: **57.0.9**.
- Device: **iPhone 17 Pro Max simulator, iOS 26.1**.
- Android: **Pixel 8 profile emulator, Android 16 / API 36**, separate temporary AVD.
- Native runtime's `Platform.constants.reactNativeVersion`: **0.86.2**.
- Final `expo-doctor@latest`: **21/21 checks passed**.
- Both tested Expo versions produced the table above on **both iOS and Android**.
  Each platform/version run contains ten requests (five per implementation).
  Every body remained
  exactly 12 bytes and `test payload`; only the Blob headers differed.

These tests prove header overwriting in the named native Expo Fetch path.
They do not prove a particular application's S3 403 cause, and do not claim
web, physical-device, or standalone-release-build reproduction.
